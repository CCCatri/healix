# Healix

**One sentence.** Healix reads a file's own patterns for internal consistency: it identifies possible matches despite different spelling, conflicts despite identical spelling, and outliers for the user to review, and answers yes / no / can't tell with what led to each answer. Internal consistency is not real-world correctness: a "yes" means the records agree with each other under the checks run, not that they are the same entity in the world. The goal it is held to is to add no false matches; so far that is measured only on the test sets named below.

**Why it exists, in my words.** Healix is a tool I developed based on the clear gaps found in inefficiently attempting to vibe code large projects with LLMs. Then I was contracted to build the LeNoble Lumber learning platform, in which I tried to do with an LLM.. this turned out chaotic and inefficient.. which brought me back to completing Healix. Hallucinations are context failures, Healix makes context failures unconstructable. Healix6 shows it took 5 previous iterations to finally understand that we were building a house on gravel never really knowing what variables we were measuring. The previous versions of Healix ballooned to hundreds of files due to hardening lies that were allowed through side doors.. but now I realize focused restraint is better. I do not want strings, sentinels, as casts, guards, shorthand, aliases to exist in the project. The judge needs established from the start as a verification layer through Healix, used to dogfood itself to verify its own product through the iterative development.

## The commands

Three npm scripts exist (`package.json`): `demo`, `gate`, `run` (and `states`, which reads `.gate/history`). They do different things and establish different things.

**`npm run demo -- <tests dir>`** (`scripts/demo.ts`). Runs the judge's pipeline on three tables and prints one screen of sentences: `c2_copy` (two built tables of copies, `<tests dir>/positive/c2_copy/tableA.csv` and `tableB.csv`), `fodors_zagat` (two real tables, `<tests dir>/unlabeled/fodors_zagat/tableA.csv` and `tableB.csv`), and a "fodors chimera" built at run time from fodors table A. It writes nothing. A successful run establishes what the judge rules on those three tables on that run: how many claims, how many ruled right, refuted, or unknown. It does not establish matching accuracy on anything else. **The tests directory is not in this repo**; without it the command exits with a file-not-found error.

**`npm run gate`** (`scripts/gate.ts`). A static and ledger check over this tree. It does not run the matcher and does not rerun any benchmark. It (1) compiles every `src/` and `scripts/` file and prints the unmasked error set; (2) counts, from the syntax tree, the forms the laws forbid (casts, sentinel fills, ternaries on undefined, names under two words, functions defined in more than one file, exports nothing imports, product files importing judge files, absence tests and fills) and prints them as `LAW` lines against the ceilings in `.gate/laws.tsv`; (3) checks the ledgers: every row of `.gate/reads.tsv` (six columns) and `.gate/verdicts.tsv` (four columns: check, verdict `approved`|`refused`, supersedes, reason) has its shape, every verdict supersedes the check's previous one, and the open refusals are counted; (4) checks the ledgers against the newest point in `.gate/history` (laws unchanged, reads and verdicts extending their copies byte for byte, a verdicts-only landing changing no source). It writes `.gate/files.tsv` (sha256 of every `src` and `scripts` file) on every run. A successful run establishes that the tree as committed is inside its ceilings and that the ledgers are well formed; it establishes nothing about match results. **As committed, the gate does not complete from a clean clone**: it requires `.gate/audit/` (gitignored) and `.gate/history/` (untracked), see *Reproducibility status*.

**`npm run run -- <tests dir>`** (`scripts/run.ts`). The matcher on the six benchmark segments, with the directory layout in `segmentList` (below). Not executed here.

## Test evidence, and what it does and does not show

- **Valid cases:** the c2 copies (`c2_copy`, `c2_exact`), where every pair was built to be the same record. The intended expectation is that the judge rules these right.
- **Known-wrong cases:** the chimeras built by `constructChimera` (`scripts/demo.ts`): records stitched from fields of different rows, wrong by construction unless those rows were one entity. The intended expectation is that the judge rules none of them right.
- **Real tables:** `fodors_zagat`, `dirty`, `beer`, unlabelled here; the judge is expected to abstain ("unknown") rather than guess.
- **Where expectations come from:** the valid and known-wrong cases are constructed, so their expected answers follow from construction. The recorded results table above is what the author's Oct 18 run produced; it is a regression baseline for that run, not an independently established expectation.
- **What a run establishes:** on the inputs it was given, that the judge rejected the constructed wrong cases it rejected and accepted the constructed copies it accepted, with the counts it printed. If execution is possible, the actual printed counts, including failures and abstentions, are the evidence. It does not establish general matching correctness, and constructed examples are not labelled real-world pairs.
- **The gate's own plant:** `scripts/gate.ts` accepts extra root files as fixtures so that a planted forbidden form can be shown to count against a law ceiling. That tests the gate's counting, not the matcher.

## How the work is done

Three roles. The **owner** (me) sets the laws and rules on what a read may decide. The **builder** is an AI agent that writes and runs code, one chain per session. The **falsifier** is a separate AI session that never sees the builder's reasoning and writes every verdict into `.gate/verdicts.tsv` with its reason. A change lands only when: its targets were written before its code and name the cell it moves; every check fails its planted fault before its pass counts; no ceiling in `.gate/laws.tsv` rises; and the gate (`scripts/gate.ts`) finds zero errors. Every landing's files are hashed into `.gate/history` on the author's machine; that history is not in this repo, so a clone cannot rebuild earlier states from it. The gate also counts, in this tree's own code, the things it forbids: silent fills, `any` leaking through a typed name, guards, duplicate units, dead exports.
